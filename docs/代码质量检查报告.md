## 三、已修复问题（F-1 ~ F-3）

### F-1 🟡 系统日志明文输出 PII（DNS 域名 / IP）
- **位置**：`entry/src/main/ets/common/Logger.ets`（全部 `hilog.*` 调用）；影响所有 `Log.info/warn/error`。
- **风险描述**：日志内容含 DNS 查询域名、源/目的 IP 等浏览元数据，属个人信息。原格式串用 `%{public}s`，任何拥有读日志权限的应用都能在系统日志里看到用户访问了哪些域名，违反鸿蒙安全规范「不应将敏感个人信息输出到日志」。
- **修复措施**：将格式串统一改为 `%{private}s`。开发者仍可用 `hilog -p off -T SplashSkip -x` 查看完整内容；普通日志读取方看到 `<private>`。同步更新专属技能 SKILL.md 的日志查看命令。
- **验证方式**：重新构建 `BUILD SUCCESSFUL`；日志内容在默认日志输出中不再明文暴露域名/IP。

### F-2 🟡 `rules.json` 损坏时静默丢失全部拦截规则
- **位置**：`entry/src/main/ets/config/RuleStore.ets` 的 `init()`。
- **风险描述**：原逻辑——文件存在但 `readFile()` 失败（半写、损坏、权限异常）时，`init()` 不 `apply`，类字段默认空数组。后果：VPN 照常运行、用户无感知，但**一条规则都不生效**，拦截能力被静默关闭（严重的安全/功能退化）。
- **修复措施**：文件存在但读不出时，回退到内置 `BLACKLIST`/`WHITELIST` 默认规则并 `persist()` 写回，同时 `Log.error` 报警。保证拦截能力不静默失效，用户可随后重新导入。
- **验证方式**：构建通过；本轮新增 `test/rule-init.test.ts`（11 项），把决策抽成纯函数 `decideInit(fileExists, readable)`，用单测锁死「损坏（存在但不可读）→ `'reseed'`、绝不静默留空」这一不变式（`RuleStore.init` 已改用该函数，回归可被自动捕获）。

### F-3 🟡 诊断页「转发 Top10」加黑经格式化字符串反解域名
- **位置**：`entry/src/main/ets/pages/Diagnostics.ets` 的 `topList` / `fmtTop` / `addBlackFromTop`。
- **风险描述**：展示串为 `${count}  ${domain}`，加黑时再 `split('  ')` 反解域名。依赖「恰好两个空格」分隔，一旦计数/域名包含空格或格式微调即解析失败；且属于无谓的字符串往返，可读性差。
- **修复措施**：`@State topBlocked/topForwarded` 改为持有 `DomainCount[]` 原始结构；`topList` 直接渲染 `item.count`/`item.domain`，加黑按钮直接传 `item.domain`，删除脆弱的 `fmtTop` 反解。
- **验证方式**：构建通过；类型校验确认 `DomainCount` 直传；建议补 UI 冒烟（点「加黑」域名正确进入黑名单）。

### F-12 🟡 诊断页「加黑」按钮实际无效（F-3 修复残留缺陷）
- **位置**：`entry/src/main/ets/pages/Diagnostics.ets` 的 `topList`（`onClick(() => this.addBlackFromTop(item.domain))`）与 `addBlackFromTop(item: string)`。
- **风险描述**：F-3 把 `topList` 改为传入原始 `item.domain`（裸域名），但 `addBlackFromTop` 的形参仍是「`count  domain`」格式化串，内部用 `item.split('  ')` 反解。于是传入裸域名后 `split` 只得到 1 段、`parts.length > 1` 为假、`host` 取空串 → 函数提前 `return`，**「转发 Top10」的「加黑」按钮点击后什么都不做**（静默失败，无反馈）。该缺陷自 F-3 落地后一直存在。
- **修复措施**：将 `addBlackFromTop(item: string)` 改为 `addBlackFromTop(host: string)`，直接 `host.trim()` 后入参即裸域名，删除脆弱的 `split('  ')` 解析；内部 `store.addBlacklistDomain(h, ...)` 与回显同步改用 `h`。调用点 `item.domain` 保持不变。
- **验证方式**：构建通过；类型与调用一致；建议真机冒烟（诊断页「转发 Top10」点「加黑」应出现「已加入黑名单：<域名>」提示，且规则管理页黑名单 +1）。

## 四、建议修复（未实施，供决策）

### F-4 🟢 `getContext(this)` / `router.back()` / `router.pushUrl()` 弃用（本轮已修复）
- **位置**：`pages/Index.ets`、`pages/Rules.ets`、`pages/Diagnostics.ets`、`pages/Grades.ets`（`getContext(this)` 共 10 处）；`Rules.ets`/`Grades.ets`/`Diagnostics.ets` 的 `router.back()`（3 处）、`Index.ets` 的 `router.pushUrl()`（1 处）。
- **风险描述**：构建产生 14 条 deprecation 警告（`getContext` 与 `router.back/pushUrl` 在 API 18 起弃用）。当前 API 23 仍可用，但属规范偏离，未来大版本可能移除；且告警噪声会掩盖真正的问题告警。
- **修复措施**：`getContext(this) as common.UIAbilityContext` 统一改为 `this.getUIContext().getHostContext()! as common.UIAbilityContext`；`router.back()` → `this.getUIContext().getRouter().back()`；`router.pushUrl(...)` → `this.getUIContext().getRouter().pushUrl(...)`。已同步移除 4 个页面中不再使用的 `import router`。
- **验证方式**：`hvigorw clean` 后重新构建，**弃用警告由 14 条降至 0**，BUILD SUCCESSFUL。

### F-5 🟠 缺隐私政策与数据安全标签（本轮已起草）
- **位置**：`app.json5` 及应用市场发布资料。
- **风险描述**：应用接管全设备 DNS、处理所有 App 的域名查询，属敏感能力。应用商店上架要求提供隐私政策与数据安全标签；当前仅在 onboarding 文字声明「不解密、不上传」。作为自研调试工具运行无碍，但对外分发前必须补齐，否则会被拒审或引发合规风险。
- **修复措施**：已撰写 `docs/隐私政策.md`（v1.0），覆盖：本地处理原则、不收集/不上传的明确边界、权限说明、数据存储与安全、信息共享（仅 DNS 查询按协议转发至可配置的上游解析服务器）、用户权利、儿童隐私、政策变更与联系方式。与 onboarding 声明保持一致。
- **验证方式**：隐私政策文本已就绪、与实现行为一致；发布前需补充开发者联系邮箱并据此在 AppGallery 填写数据安全表单（F-5 剩余动作）。

### F-6 🟢 空闲轮询 10ms（100Hz EAGAIN）
- **位置**：`vpnextension/SkipVpnExtension.ets` 的 `IDLE_MIN_MS=10` / `IDLE_MAX_MS=100`。
- **风险描述**：无 DNS 包时每 10ms 一次 `fs.read` 返回 EAGAIN 并重试，空闲态约 100 次/秒系统调用。单次开销极小，但长时间后台待机时仍属持续唤醒。架构注释已说明「读到包立即回到 10ms」以保证拦截时延。
- **修复措施**：若关注待机功耗，可把 `IDLE_MAX_MS` 提高到 200–300ms（仍秒级响应，对开屏广告足够）；或改用可中断的等待。当前不改，因拦截时延优先。
- **验证方式**：`hdc shell top` 观察扩展进程 CPU 占用。

### F-7 🟢 设置页每次操作新建 RuleStore 并读盘
- **位置**：`pages/Rules.ets` 的 `store()`、`pages/Diagnostics.ets` / `pages/Grades.ets` 的 `store()`。
- **风险描述**：每次增删改查都 `new RuleStore(...).init()`（accessSync + readTextSync）。设置页交互频繁时略浪费 I/O，但与扩展进程的跨进程一致性设计（真相源恒为文件）一致，**正确性优先**，可接受。
- **修复措施**：可作为优化——在 `aboutToAppear` 缓存一次 `RuleStore` 实例（仍每次 `current()` 读文件以保证一致）。择机。
- **验证方式**：不影响功能。

## 五、确认正确的设计（非问题，供评审安心）

- **F-8 fail-open 安全默认**：`DomainRules.decide` / `decideWithSessionAllow` 在任何未命中、异常、解析失败路径一律放行。网络拦截器最安全的选择是「宁可放过、不可误杀」，避免把用户正常 DNS 打挂。`dispatch` 中未命中才转发上游，命中才构造应答。
- **F-9 权限最小集**：`module.json5` 仅申请 `ohos.permission.INTERNET`；VPN 本身由系统授权弹窗确认，未申请任何越权权限（无位置/通讯录/存储等）。符合最小权限原则。
- **F-10 checksum 用途正确**：`RuleSchema` 用 FNV-1a32 仅做**完整性**校验（防导入文件被篡改/截断），非鉴权；导入源是用户通过系统选择器显式挑选的本地文件，无远程信任问题。
- **F-11 IPv6 回包**：`buildResponsePacket` 对 IPv6 重建为纯 40 字节头（不带原扩展头/flow label）。DNS 应答是 UDP 负载，该简化对查询结果无功能影响；IPv4 则完整保留原头部（含 options）并重算校验和。
