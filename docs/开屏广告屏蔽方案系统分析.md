# 官方开屏广告屏蔽方案系统分析

> 适用对象：中国联通、中国移动、各大银行、政务、运营商等**自带官方开屏广告**（非第三方广告 SDK 投放）的 App。
> 分析目标：从技术类别、适用条件、权限环境、优缺点与风险、用户分群推荐五个维度，系统梳理可行的跳过或屏蔽方案。
> 数据来源：本工程 `harmony-splash-skip` 对**中国联通 App** 的真机实测（A/B/C 三轮对照、4 张证据图），以及 `docs/真机PoC验证手册.md`、`docs/ADR-001-DNS拦截架构决策.md` 的论证结论。

---

## 〇、先讲清楚一个关键前提：官方广告 ≠ 第三方广告

这是整个分析的分水岭，必须先点明。

| 维度 | 第三方 SDK 广告（穿山甲／广点通／优量汇等） | 官方自带开屏广告 |
| --- | --- | --- |
| 内容来源 | 广告联盟的独立域名（如 `ad.qq.com`、`pangle.io`） | App 自己的业务域名（如 `10010.com` 子域）或**打包在 App 本地资源** |
| 与功能耦合 | 弱（拦掉不影响主功能，最多少块图） | 强（同源、甚至本地，拦了可能闪退或功能缺失） |
| 网络层可拦性 | **极高**（独立域名一拦一个准） | **极低**（无干净可拦域名，或根本没有网络请求） |
| 实测结论 | 本工程拦截效果 A/B 级 | 联通实测三轮 **E 级**（拦 26 次广告仍完整播放） |

**结论先行**：网络层手段对"第三方 SDK 广告"是降维打击，但对"官方自带开屏广告"几乎无效。官方广告只能从两个方向解决——**模拟用户点击跳过（自动化）** 或 **修改 App 自身逻辑（应用层）**。下文所有方案都围绕这个前提展开。

## 一、按技术类别梳理各方案

### 类别 A：网络请求过滤（不改 App，改流量）

| 编号 | 方案 | 一句话原理 |
| --- | --- | --- |
| A1 | **本地 VPN 隧道 DNS 拦截**（本工程采用） | 建本地虚拟网卡，截获 DNS 查询，命中黑名单返回 `0.0.0.0`／`NXDOMAIN` |
| A2 | 局域网 DNS 拦截（AdGuard Home／Pi-hole） | 把路由器 DNS 指向自建拦截服务，全屋生效 |
| A3 | 本地 HTTP 代理 + 证书（mitmproxy） | 中间人解密 HTTPS，按接口／响应体精细拦截或篡改跳过逻辑 |
| A4 | 系统 HOSTS 文件修改（需 root） | `/system/etc/hosts` 把广告域名指向 `127.0.0.1` |
| A5 | DoH／DoT 重定向拦截 | 针对加密 DNS（端口 853／443），重定向到自建解析 |

### 类别 B：系统级拦截

| 编号 | 方案 | 一句话原理 |
| --- | --- | --- |
| B1 | Root + hosts／AdAway | 系统层全局域名屏蔽 |
| B2 | 厂商系统广告开关 | 小米／华为／OPPO 等"系统工具广告"开关 |
| B3 | 鸿蒙系统级广告管理 | 当前 HarmonyOS 无统一开屏管理，依赖 App 自律 |

### 类别 C：应用逻辑修改（动 App 本体）

| 编号 | 方案 | 一句话原理 |
| --- | --- | --- |
| C1 | 反编译重打包（apktool + smali） | 解包→删开屏 Activity／改倒计时→重签名 |
| C2 | Xposed／LSPosed 模块钩子 | 运行时 Hook 开屏逻辑 |
| C3 | Frida 动态注入 | 研究用，注入脚本绕过开屏 |
| C4 | 第三方"去广告版"App | 下载非官方修改包（**高危**） |

### 类别 D：自动化操作（模拟人手）

| 编号 | 方案 | 一句话原理 |
| --- | --- | --- |
| D1 | **无障碍服务自动点击"跳过"**（最务实兜底） | 检测"跳过广告"按钮并模拟点击 |
| D2 | 自动化脚本（Tasker／Auto.js／鸿蒙元服务自动化） | 触发式执行点击 |
| D3 | 硬编码坐标点击 | 固定坐标模拟点击（最脆弱） |

### 类别 E：官方合规途径

| 编号 | 方案 |
| --- | --- |
| E1 | 付费会员去广告（部分运营商 App 有，但开屏常仍保留） |
| E2 | 监管投诉（工信部对"摇一摇""关不掉"等违规开屏已整治，但合规开屏仍允许） |

## 二、各方案适用条件、所需权限／环境

### A1 本地 VPN DNS 拦截（本工程方案）
- **适用条件**：无需 root；Android／HarmonyOS 均可；需用户手动授权 VPN 并**始终开启**。
- **权限／环境**：VPN 权限（系统弹窗授权）、前台服务通知权限、网络权限。
- **对官方广告**：同源域名不能拦（会连累功能），本地资源根本无请求 → 实测 E 级；仅对第三方 SDK 广告有效。

### A2 局域网 DNS 拦截
- **适用条件**：需一台 7×24 运行的设备（树莓派／NAS／软路由）；手机连该 WiFi。
- **权限／环境**：网络管理员权限；自建设备维护。
- **局限**：仅 WiFi 有效，蜂窝网络无效；对官方域名同源问题同样无解。

### A3 mitmproxy 代理
- **适用条件**：需安装并**手动信任自定义 CA 证书**；配置 WiFi 代理。
- **权限／环境**：用户证书信任（Android 7+ 对普通应用需手动信任，鸿蒙更严）；HTTPS 证书固定（cert pinning）的 App 无法解密。
- **门槛**：证书安装与代理配置对普通用户极不友好。

### A4 / B1 hosts 修改
- **适用条件**：**必须 root**；系统可写。
- **权限**：root 文件系统写权限；系统更新可能覆盖。

### B2 厂商广告开关
- **适用条件**：仅限对应品牌系统 App 的部分工具广告；**对第三方 App 和官方内容广告无效**。

### C1–C3 应用逻辑修改
- **适用条件**：C1 需原包可重签名（多数有签名校验／防篡改，鸿蒙 HAP 完整性校验使其几乎不可行）；C2 需 root + 框架（**鸿蒙 NEXT 无 Xposed 生态**）；C3 需 root 或越狱 + 对抗加壳／反调试。

### D1 无障碍自动点击
- **适用条件**：无需 root；需开启**无障碍权限**；依赖屏幕上出现"跳过／跳过广告"按钮。
- **权限／环境**：无障碍服务常驻；后台受限（部分系统杀无障碍）。

### D3 坐标点击
- **适用条件**：无需特殊权限，但高度依赖固定 UI 布局，分辨率／版本一变即失效。

### E 官方途径
- **适用条件**：钱包决定；合规，无技术门槛。

## 三、各方案优缺点与潜在风险

| 方案 | 优点 | 缺点与风险 |
| --- | --- | --- |
| **A1 VPN DNS** | 无需 root；系统级对所有 App 生效；规则可热更新；**第三方 SDK 广告拦截极好** | ①对官方广告实测 E 级（同源／本地资源无解）②需常开 VPN，耗电、与别的 VPN／游戏加速器互斥③DNS 失败可能致 App 启动变慢或闪退④鸿蒙 NEXT 后台 VPN 管控更严，待机可能被回收 |
| A2 局域网 DNS | 全设备覆盖、零客户端改造、不耗手机电 | 仅 WiFi；同样对官方域名无解；需维护硬件，断电全家断网 |
| A3 mitmproxy | 精细到接口／参数，理论上能拦分离的官方广告接口 | 证书安装门槛极高；**法律风险（解密流量）**；证书过期致大量 App 连不上；cert pinning 无法解密；耗性能 |
| A4/B1 hosts | 全局生效、零额外进程、省电 | 必须 root（失保／安全风险）；系统更新覆盖；官方域名同源无解；维护麻烦 |
| B2 厂商开关 | 官方、零门槛、合规 | 覆盖面窄，对第三方 App 与官方内容广告无效 |
| C1 重打包 | 改得彻底 | 签名校验／防篡改难破；鸿蒙 HAP 完整性校验几乎不可行；**分发自用违法风险** |
| C2 Xposed | 运行时精确 Hook | 需 root + 框架；**鸿蒙 NEXT 无生态**；框架本身稳定性／安全风险 |
| C3 Frida | 研究灵活 | 需 root／越狱；对抗加壳反调试难；仅适合研究 |
| **C4 修改版 App** | 看似省事 | **极高风险：木马／隐私泄露／账号被盗；违背合规；强烈不推荐** |
| **D1 无障碍点击** | 不改网络、不拦请求；**对官方广告反而最稳**（官方必有可点"跳过"）；合规边界较好 | 需等倒计时（或抢可点瞬间）；按钮文案／位置多变需适配；无障碍后台受限；误点风险 |
| D2 自动化脚本 | 灵活可编排 | 配置复杂；同 D1 的适配与后台限制 |
| D3 坐标点击 | 最简单 | 分辨率／UI 一变即失效，最脆弱 |
| E 官方途径 | 合规、无忧 | 开屏常仍保留；花钱 |

## 四、按用户技术水平推荐

### 小白用户（不想折腾）
- **首选**：系统自带广告开关（能关的关掉）+ 官方会员（若划算）+ 手动点"跳过"。
- **不推荐**：任何需要 root、证书、代理、重打包的方案。
- **底线**：绝不下"去广告版"第三方包。

### 进阶用户（会用 App、愿装一个工具）
- **推荐组合拳**：
  1. 安装本工程的 **VPN DNS 拦截工具**——清掉穿山甲／广点通等**第三方 SDK 广告**（A 级效果）；
  2. 叠加**无障碍自动点击"跳过"**（D1）——兜底清掉官方自带开屏（这是网络层做不到的）。
- 这一组合是当前**对非技术用户最务实、合规、见效**的路径。

### 极客／有 root 用户
- hosts／AdGuard Home 局域网拦截（A2/B1）+ 无障碍（D1）；仍**不碰修改版 App（C4）**。
- 可在家部署 Pi-hole，全屋设备受益。

### 开发者／研究者
- 本项目路线（VPN DNS 引擎 + 规则热重载 + 校验）+ 后续 **R-12 规划的辅助点击能力**；
- Frida 用于逆向验证开屏逻辑（研究用途）；
- 关注官方合规边界，工具定位于"跳过"而非"破解"。

## 五、核心结论与本项目演进方向

1. **官方自带开屏广告的本质难点**是"第一方、常本地化、与功能耦合"，网络层无干净可拦目标。这一点已被联通 App 三轮实测（E 级）坐实。
2. **没有单一银弹**：网络层（A1）解决第三方 SDK 广告，自动化点击（D1）解决官方开屏，二者互补。
3. **本项目当前能力**：已完成 A1（VPN DNS 拦截 + 规则 CRUD + 导入导出校验 + 效果分级），对第三方广告达标；对官方广告如实标注 E 级未达标。
4. **演进方向（已列入规划 R-12）**：引入无障碍辅助点击／"跳过"检测，补齐官方开屏这一块短板，形成"网络拦第三方 + 点击跳官方"的完整闭环。
5. **合规红线**：坚持"拦截第三方广告 + 自动跳过官方广告"的定位，不碰重打包、不碰修改版 App、不解密用户隐私流量。
